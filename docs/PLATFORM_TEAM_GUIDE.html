Meeting Minutes AI Service

Three endpoints that turn a board-meeting recording into structured Arabic minutes and extracted decisions.

Overview

You give us a meeting video URL and your meetingId. We transcribe it, draft the minutes, and extract the decisions. You poll until it is done, then read the result once.

POST /v1/meeting-minutes Accepts the job. Returns 202 immediately — it does not wait for minutes.
GET /v1/meeting-minutes/{meetingId}/status Poll every 5–15 s until COMPLETED or FAILED.
GET /v1/meeting-minutes/{meetingId} The minutes and decisions. Only after COMPLETED.
The one thing to internalise

A meetingId is one job, forever. We never mint a second ID. POSTing the same ID again returns the existing job — it never regenerates, and it never retries a failure. Everything else follows from this.

Do not build a “resubmit to repair” path

A re-POST ignores every field except meetingId. Submitting the same ID with a corrected videoUrl does not update the job, does not retry it, and still returns 202 — so it looks like success while silently doing nothing. The job stays bound to the original URL.

Fixing a bad URL requires a new meetingId. A FAILED job stays failed until an operator resets it, which is not a public API.

02Poll the status

Returns 200 whenever the job exists — including failures, because the lookup itself succeeded. Only an unknown meetingId is a 404.

GET /v1/meeting-minutes/{meetingId}/status → 200in progress
{
  "success": true,
  "data": {
    "meetingId": "cm123platformMeetingId",
    "status": "PROCESSING",
    "progress": 65,
    "stage": "GENERATING_MINUTES",
    "updatedAt": "2026-09-07T10:34:20Z"
  }
}
statusMeaning
QUEUEDWaiting behind another meeting, or waiting for disk space to download the video. Both clear on their own — keep polling, do not resubmit.
PROCESSINGDownloading, splitting audio, transcribing, or generating.
COMPLETEDSafe to fetch the minutes.
FAILEDTerminal. Read data.error. Do not POST the same ID to retry.

progress is an integer 0–100 and never moves backwards. stage is a closed set you can safely switch on: QUEUED, TRANSCRIBING, GENERATING_MINUTES, COMPLETED. On failure it reports the stage where the job died.

03Read the minutes

Call only once status is COMPLETED. Repeat reads return the identical payload and never start a new job — but persist it on your side anyway; this endpoint is not your system of record.

Rules for content.sections

  • content is a JSON object, never a JSON-encoded string.
  • sections is always exactly these five, in this order: meeting_info, attendance, introduction, agenda, main_items. Nothing is dropped, nothing else is added — so you can render fixed slots without null-checking the list.
  • title is model-generated Arabic prose and may be "". Key your layout, translations and storage off key, never off title.
  • content is Markdown and may be "". An empty section is legitimate — it means the recording never stated it.
  • Decisions never appear inside sections; they are only in the top-level decisions array.
  • Missing facts come back as "", null, or an Arabic “not stated” line. None of these is a transport error. Persist them as-is — we deliberately do not invent names, dates, attendance or deadlines.

Check the body, not just the status

Reading minutes too early returns 200 with success: false, not a 4xx. A client that branches on res.ok alone will treat it as a success and read data as undefined. Always check body.success.

There is no transcript in this response — it is an operations artefact, not part of the contract.

Client implementation

A correct client, with the four traps already handled: success checked separately from res.ok, 503 retried, terminal states distinguished, and optional decision keys read safely.

TypeScriptreference client
const BASE = process.env.AI_SERVICE_BASE_URL!;
const KEY  = process.env.AI_SERVICE_API_KEY!;
const headers = { Authorization: `Bearer ${KEY}`, "Content-Type": "application/json" };

// 503 means "try again shortly", never "this meeting failed".
async function call(path: string, init?: RequestInit) {
  for (let attempt = 0; ; attempt++) {
    const res = await fetch(BASE + path, { ...init, headers });
    const body = await res.json();
    if (res.status === 503 && attempt < 5) {
      await sleep(2 ** attempt * 1000);
      continue;
    }
    return body; // caller inspects body.success — NOT res.ok
  }
}

export async function generateMinutes(meetingId: string, videoUrl: string) {
  const submitted = await call("/v1/meeting-minutes", {
    method: "POST",
    body: JSON.stringify({ meetingId, videoUrl, language: "ar" }),
  });
  if (!submitted.success) throw new Error(submitted.error.code);

  // Hours, not minutes. Run this in a job queue, never in a request handler.
  for (;;) {
    const { data } = await call(`/v1/meeting-minutes/${meetingId}/status`);
    if (data.status === "FAILED") throw new Error(data.error.code);
    if (data.status === "COMPLETED") break;
    onProgress?.(data.stage, data.progress);
    await sleep(10_000);
  }

  const result = await call(`/v1/meeting-minutes/${meetingId}`);
  if (!result.success) throw new Error(result.error.code);

  return {
    sections: result.data.content.sections,   // always the same 5, in order
    decisions: result.data.decisions.map((d) => ({
      ...d,
      // omitted, not null — normalise once, here
      ownerName: d.responsiblePersonName ?? null,
      durationDays: d.completionDurationUnit === "DAYS" ? d.completionDuration : null,
    })),
  };
}

Capacity — please design around this

v1 runs on a small CPU-only VM with no GPU. The speech model and the language model cannot be loaded at the same time, so jobs run strictly one at a time, first in first out.

Recording lengthExpected wall clockNote
3 minutes16 minMeasured on the live deployment — 5.4× the recording length.
60 minutes~5.5 hoursExtrapolated from that rate.
90 minutes~8 hoursA typical board meeting.
  • Submit from a background job, never inside a web request.
  • A second meeting submitted while one is running sits at QUEUED for the whole first job. That is expected, not a fault.
  • Tell users “minutes will be ready later today”, not “in a few minutes”.
  • Poll every 5–15 seconds. There is no webhook in v1.
